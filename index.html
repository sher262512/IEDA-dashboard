「检测 → 修复 → 回跳」闭环（点工具不进主流程）

「不在主流程」的确切含义：检测是主流程每步内嵌的 check 节点。检测结果三种：①无违规→直接下一步；②确定是上游代码问题/无法处理→记录后直接下一步；③检测到可处理的违规→才调用修复点工具，修复后回到之前对应步骤重新跑通。

点工具作用触发条件回跳目标
eco_repair_via修复 via 类 DRC 违例检测到 via/cut/enclosure 类 DRC 违例回到布线后 DRC 检测步骤重新检测
sta_supplement补充/重跑 STA主流程缺 STA，或需对某阶段 DEF 重做时序分析并入对应时序分析步骤记录
drc_supplement补充/重跑 DRC主流程缺 DRC，或需重检回到布线后 DRC 检测步骤

这三个点工具位于各案例 fix/ 目录（specs.json + steps/*.sh + prompts/*.md），不在主流程 specs.json 顺序里，仅在检测失败后按需人工触发。

关键差异（含确切原因）

① tapcell（ihp130 缺失）

确切原因：SG13G2 标准单元库不提供 tap/endcap/welltie 单元（库里只有 decap 去耦电容和 fill 填充，都不具备阱接触/防闩锁的 tap 功能）；而 iFP 又没有 cut_rows（切行）这个替代能力，所以官方流程把 tapcell 整段注释掉了。官方脚本注释原文：There are no Endcap and Welltie cells in this PDK, so `cut_rows` has to be called from the tapcell script. But yet iFP has no cut_rows support.

② 时序收敛链（STA×3 + DRV/hold）—— 仅 sky130 有

确切原因：sky130_gcd 的 28 步继承自项目已有的 p7 基线（40 步手工完整流程），显式包含 sta_after_cts/drv/hold 三次 STA、fix_drv、fix_hold。ihp130/ics55 则直接自官方 iEDA-Script 的 run_iEDA.sh 主流程（仅 8 会话）拆解而来，不含 STA/TO 环节；两者的 STA/TO/DRC 脚本虽存在于官方仓库，但未被 run_iEDA.sh 串入主流程，属孤立脚本（未接入主流程的脚本）。

③ DRC 检查 —— 仅 sky130 有

确切原因：sky130 的 p7 基线显式执行了布线后 DRC(25/26) 与填充后 DRC(27)；ihp130/ics55 的官方主流程未包含 DRC，现通过 fix/drc_supplement 补检。

④ 步骤粒度（sky130 更细）

确切原因：sky130 继承 p7 基线"一条入口=一条 Tcl 命令+共享会话"设计（CTS 拆 14/15、布线拆 22/23/24）；ihp130/ics55 沿用官方 run_iEDA.sh 的自包含脚本（run_iCTS.tcl 一次做 run_cts+cts_report，run_iRT.tcl 一次做 init_rt+run_rt+destroy_rt），每阶段=独立会话=一步。本质是同一批命令按不同粒度分组。

⑤ init_floorplan 方式

确切原因：sky130/ihp130 用固定面积（-die_area/-core_area）；ics55 用利用率（-core_util 0.2）。这是各案例官方脚本自身的 USE_FIXED_BBOX 开关选择。

ics55_gcd —— 问题诊断（问题 / 来源 / 成因 / 结果）

问题来源成因导致的结果
CTS 时钟树综合崩溃（原生缺陷）第 14 步 build_cts 的 session 日志（BoundSkewTree.cc:1879 处 LOG_FATAL）use_skew_tree_alg=ON 启用了 BoundSkewTree 时钟树算法。在 34 个时钟 sink 与顶层厚金属（MET5/T4M2/RDL）单位 RC 的组合下，算法在合并时钟树时计算两点间走线的 Elmore 延迟增量，得到负值。延迟增量表示“增加一段走线后信号到达时间的变化量”：正值意味着信号更晚到达（正常），负值意味着加线后信号反而更早到达——这在物理上不可能（走线只会增大 RC 延迟、使信号更晚到达），因此算法判定内部状态或 RC 数据已出错，触发断言 'point increase delay is negative' 并终止进程iCTS_result.def 未生成，后续 15-18 步（legalize / route / filler / GDS）因此断链、未能运行
